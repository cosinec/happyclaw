# 决策与风险

## 需要拍板的决策

### D1：iOS 分发方式

| 选项 | 成本 | 限制 | 适合 |
|---|---|---|---|
| 个人自签（SideStore/AltStore） | 低 | 7 天续签；免费账号通常不支持 Push/Widget | 个人自用、先验证体验 |
| 付费开发者账号（TestFlight/Ad Hoc） | $99/年 | 需要证书/续期管理 | 要推送/Widget/多人使用 |
| App Store | 高 | 审核、隐私政策、上架规则 | 公开分发 |

**建议**：先个人自签做 MVP；推送/Widget 之前再评估是否升级付费账号。

### D2：推送方案

| 选项 | 成本 | 体验 | 风险 |
|---|---|---|---|
| Web Push（PWA） | 低 | 必须添加到主屏幕；后台投递受 iOS 限制 | 用户没装 PWA 就收不到 |
| APNs（原生） | 中（证书/Key/付费账号） | 最好，可角标/深链 | 证书管理、审核 |
| 两者都做 | 高 | 覆盖最全 | 维护两套 |

**建议**：先 Web Push 验证需求；原生壳稳定后再补 APNs（或只保留 Web Push）。

### D3：i18n

| 选项 | 成本 | 收益 |
|---|---|---|
| 只做中文 | 0 | 保持现状 |
| 中英双语 | 中（抽词条 + 翻译 + 测试） | 可分享给英文用户/开源 |

**建议**：本轮不做；先抽词条结构（不翻译），为以后留口子。

### D4：原生 Sheet 实现

| 选项 | 成本 | 风险 |
|---|---|---|
| 子 WKWebView + 原生 Sheet | 低 | 状态与主 WebView 分离 |
| 同一 WebView + 原生 Sheet 容器（MP 做法） | 中 | 实现复杂，但状态统一 |
| 复杂弹窗继续 Web，简单列表用原生 | 低 | 体验不完全统一 |

**建议**：MVP 用“简单列表原生 + 复杂弹窗 Web”；Phase 4 再评估统一到 MP 做法。

### D5：是否上可拖拽 Dashboard

**建议**：Phase 5 可选。先把 Monitor/Usage 做扎实，不要为了 dashboard 引入 GridStack。

| R-11 | 搜索/日志拖慢主线程 | 中 | 中 | 后端分页/索引；前端虚拟化/批量刷新；性能预算 |
| R-12 | 通知过多刷屏 | 中 | 中 | 去重/分组/静默规则；前台不弹系统通知 |
| R-13 | 后台挂起导致流式丢失 | 高 | 中 | 回前台重连 + 增量 + 恢复快照 |

| R-15 | App Store 审核/隐私政策 | 低（暂不上架） | 中 | 本轮不做；以后评估 |

## 待确认的问题

1. **用户规模**：只自己用，还是给家人/朋友用？影响推送、多用户、App Store 决策。
2. **iOS 最低版本**：iOS 17 可以吗？是否必须支持 iOS 16？
3. **iPad**：这轮是否需要 iPad 布局？
4. **推送需求**：哪些事件必须推送？（任务完成/审批/后台任务/全部）
5. **数据量级**：会话数、消息数、文件数大概多少？影响搜索/索引方案。
6. **后端可用性**：搜索 API、通知事件、Push 订阅表由谁做？工期是否在本次范围？
7. **许可证**：HappyClaw 是否开源/分发？决定能否参考 MIT 代码、GPL 边界。
8. **设计资源**：是否有 Figma/视觉规范？原生壳的 TabBar/Sheet 是否要统一品牌色？
9. **测试设备**：有几台 iPhone/iOS 版本可测？
10. **上线节奏**：是否接受每 1–2 周一个 Phase 的节奏？

## Reviewer 重点挑战

- Phase 0 是否应该先做「搜索/通知」而不是治理？
- iOS 壳 MVP 是否还能再砍？例如第一版不做 Passkey/Widget。
- Phase 2 的 chat 拆分是否风险过高？是否应该延后到 iOS 之后？
- 推送选 Web Push 是否足够？APNs 的成本是否值得？
- 是否有漏掉的多用户权限/隐私问题？
- 原生壳与 Web 的职责边界是否清晰？会不会出现两套状态？
